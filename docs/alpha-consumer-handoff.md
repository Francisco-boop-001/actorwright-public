# Actorwright preview.260 private alpha consumer handoff

This runbook is for the binary-only mod-work consumer. Use it only with the
separate Exchange release-candidate and APPROVED promotion bundle that bind the
exact `1.0.0-preview.260` bytes. Merely finding the candidate in the Exchange
does not activate it.

## What this alpha proves

The packaged CLI preserves all 136 protocol-v1 command names. Its protocol-v2
capabilities and schema exports are generated by the exact packaged executable
and shipped under `evidence/`. The admitted agentic slice can discover a copied
workspace, persist and inspect an exact RaceMenu JSlot, perform static NPC
preflight/build work, produce an off-engine preview, and independently verify a
Finish artifact when the required inputs already exist.

This alpha does **not** prove Skyrim runtime behavior, human visual acceptance,
placement, pathing, recruitment, conflict freedom, promotion of an NPC mod, or
public-release readiness. `gui`, `npc finish analyze`, and `npc finish apply`
remain Legacy and unadvertised under protocol 2; the GUI/Finish review and
receipt surfaces remain deferred. The local operation journal is optional
diagnostic evidence, not workflow state.

## Acquire and admit the candidate

The paths below are examples; substitute your configured exchange directory.

1. Obtain the new no-overwrite candidate directory from
   `K:\ExampleExchange\releases\candidates` and the separate human-approved
   promotion bundle from `K:\ExampleExchange\releases\approved`.
2. Require the promotion decision to be `APPROVED` and its
   `candidateManifestSha256` to equal the SHA-256 of the candidate's exact
   `bundle-manifest.json` bytes.
3. Before `analyze`, have the consumer repository prepare a fresh preview.260
   target manifest from the candidate's exact release metadata. The installer's
   `-ManifestPath` must identify that target manifest, not the still-active
   preview.242 manifest. Keep the active manifest and wrapper unchanged at this
   point.
4. Use the consumer repository's own release `analyze`, `apply`, then `verify`
   procedure with the same preview.260 target manifest in all three modes.
   `analyze` must read the human-approved promotion bundle from
   `releases\approved`; `issues\responses` is the product-response lane and is
   never a promotion input. Do not copy Actorwright source or point a wrapper
   into the product repository.
5. Only after `verify` succeeds, update the consumer's tracked active manifest,
   exact wrapper path, registration, and rollback metadata as one reviewed
   consumer change; then verify the live wrapper identity.
6. Preserve the previously approved consumer as rollback. Install into a fresh
   version-specific directory; never overwrite an existing installation. If the
   destination already exists, use `verify` against the target manifest to
   check that installation; do not rerun `apply` or weaken the no-overwrite
   rule.
7. Verify the installed CLI SHA-256 against the candidate inventory before use.

The historical `NPCM-20260815-0001` record captures the expected refusal when
the active preview.242 manifest is incorrectly passed as the preview.250
target: the installer compares the correct preview.250 ZIP against preview.242's
pinned ZIP hash and reports `package hash mismatch`. Preserve that rollback
evidence and do not weaken the check. For preview.260, provide the exact
preview.260 target manifest from the approved candidate instead. Preview.258,
Preview.257, Preview.256, and Preview.255 remain the preserved rollback
identities and must not be mixed with the current preview.260 target manifest.

## PowerShell launcher in future release builds

The release builder now includes `cli/actorwright.ps1` beside the executable.
Invoke it from PowerShell with quoted FormKeys, for example:

```powershell
& '<approved-install>\cli\actorwright.ps1' npc inspect --help
```

Arguments such as `'Provider Name.esp|0x00000800'` stay a single argument, and
`$LASTEXITCODE` receives the executable's exit code. Use the exact installed
binary's schema export to discover the options for a command. This source
change does not add a launcher to previously packaged or installed releases.
The retained `npcm.cmd` route passes through `cmd.exe`; values containing `|`
must remain double-quoted at that layer. Prefer `actorwright.ps1` when calling
from PowerShell.

## Discover the exact alpha contract

Set both roots to fresh ordinary directories below the mod-work repository:

```powershell
$env:ACTORWRIGHT_WORKSPACE_ROOT = '<K-local-mod-workspace>'
$env:DOTNET_BUNDLE_EXTRACT_BASE_DIR = `
  '<K-local-mod-workspace>\artifacts\actorwright-bundle-extract'
$cli = '<approved-install>\cli\actorwright.exe'

& $cli version --protocol 2 --json
& $cli capabilities --protocol 2 --json
& $cli schema export --protocol 2 --json --command 'workspace preflight'
& $cli schema export --protocol 2 --json --command 'npc create-from-jslot'
```

Treat the installed binary output as authoritative. The release also contains
`evidence/capabilities.json` for protocol 1 and
`evidence/protocol-v2-schema-exports.json` for every command the exact binary
advertised as `readiness: "v2"` when packaged. Refuse the installation if its
live identity or schemas differ from that evidence.

## Aelva consumer checkpoint

The Aelva input consists of the exact `.jslot`, chargen NIF, and chargen DDS
identified in the handoff evidence. The mod-work creator must materialize a
fresh K-local copied Data closure and effective load order for `Skyrim.esm`,
`High Poly Head.esm`, `KS Hairdo's.esp`, `Koralina's Eyebrows.esp`, and
`Tullius Eyes.esp`, including the selected KS Envy hair, Koralina eyebrow,
PayEyes, mouth/head textures, skin selector textures, and face overlays.

Use the live protocol-v2 capability rows and schema exports to construct, in
order. For the request document, select the `result.documentSchemas` entry
whose `name` is `request`, `direction` is `input`, and
`schemaIdentifier` is `npc.create-from-jslot.request.v1`; use its closed
Draft 2020-12 `jsonSchema`. This is the existing schema-discovery surface, not
a new validator or command, and the request must not be reverse-engineered
from an older project.

1. `workspace preflight` with a fresh reviewed-intake and workflow output. Its
   `--output-root` is retained in the reviewed-intake binding and is reserved
   for that intake; its parent directory must already exist. Do not use the
   intake `--output-root` as the later package request's `output.root`.
2. `preset inspect` with the exact uppercase JSlot SHA-256 and a fresh receipt;
3. `npc create-from-jslot` preflight, then its reviewed-preflight build mode;
4. `preview npc` with the exact package manifest, reviewed intake, workflow,
   plugin, FormID, and fresh output roots.

The package request's `output.root` must be a different fresh path from the
retained reviewed-intake `--output-root`; create its parent before admission.
If the preflight reports a missing output-root parent, fix that parent and keep
the intake output path unchanged. Every output path must otherwise be fresh.
Preserve every envelope, workflow bundle,
artifact, package manifest, preview bundle, hash manifest, contact sheet, six
views, and local operation journal record. The package gate validates the
preview schema, but authentic preview execution is deliberately
`consumerRequired` because only the mod-work environment owns the dependency
closure and external renderer installation.

Before treating a body skin as packaged, inspect the produced
`whole-skin-authority.json`. A route of `inherited-race` means body, hands, and
feet use the shared race texture paths; preparing a per-NPC body texture does
not make it part of the package. A per-NPC body skin requires a private
ARMO/ARMA/TXST closure admitted and emitted by the request. This static route
statement does not establish Skyrim runtime or visual authority.

## Return evidence to Actorwright

On success or first refusal, return a sanitized issue bundle through the
Exchange incoming lane containing:

- exact installed version, source line, CLI SHA-256, candidate-manifest SHA-256,
  and capabilities SHA-256;
- exact command, exit code, outcome, diagnostics, effects, authority, and next
  actions;
- hashes and sizes for the admitted input and produced artifacts;
- renderer dependency diagnostics and the preserved preview images when they
  are redistributable;
- expected versus observed behavior, without credentials, live-game paths, or
  unrelated modlist contents.

Runtime testing and subjective likeness acceptance belong to the user. They are
reported separately and never inferred from static or off-engine evidence.
